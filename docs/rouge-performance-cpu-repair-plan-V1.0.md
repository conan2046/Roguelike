# 战斗CPU性能修复方案 V1.0

日期：2026-10-25。状态：用户已确认“按方案连续修复”。范围为正式战斗核心的技术性能修复，不新增玩法；依次实施P0—P3并记录证据。

## 问题与证据

完整报告：`rouge-performance-report-20261025.md`。合法测试场地、出生重叠/越界均为0、Burst实际运行时，500/1000/2000三档均未达到现有TbPerformanceScenario的60FPS目标，模拟欠账持续增长。

500档短时CPU阶段诊断：模拟P95约125.7ms，MoveAndIndex约124.5ms；按采样各阶段累计时间，移动阶段占约99.28%。攻击、弹丸、区域与伤害并非当前主瓶颈。阶段诊断包含Profiler开销，仅用于定位，不替代完整60秒样本。

当前MoveAndIndex逐单位更新空间索引，MoveCylinder每次接触扫描网格候选并经ComponentLookup读其他单位，接触迭代上限随单位总数增长。需进一步区分组件随机读取、候选重复与零进展滑移的成本，不能只凭阶段总时间断言全部来自某一行。

## 拟定边界

- 正式Excel、Luban结构/生成物、属性、概率、时间线、AI速度、武器伤害/范围、移动阻挡规则及碰撞体尺寸不变。
- 保留地面/飞行的现有碰撞语义、源表中心偏移、玩家优先与稳定槽位顺序；不以缩小碰撞体、关闭阻挡或放慢模拟换取帧率。
- 不覆盖Scene/Prefab，不修改手调Transform，不生成预览资产，不构建Win64、不提交或推送。
- 不同时改透明渲染策略、Shader、URP路径或血条样式。渲染DrawCall线性增长是后续风险，先用CPU证据决定是否需要另立渲染批次。

## 数据流与所有权

Luban配置→现有CombatSessionSettings/属性快照→本Tick原生状态→碰撞/攻击/伤害→统一写回ECS→现有ANI/反馈/UI。模型、资源服务、随机序列与事件链继续沿原入口。

可新增的仅为技术数据：阶段/候选/接触计数，以及会话拥有的原生状态缓冲。它们不构成第二套配置或默认值，容量由当前实际槽数推导；扩容只在Job完成后执行，重开清空，Dispose释放。Profiler标记名和数值求解的终止条件属于技术边界，不引入策划可调参数。

## 分批执行

| 门禁 | 工作 | 必须保留的证据 |
|---|---|---|
| P0 基线冻结 | 保存当前源表/手调资源哈希、逐Tick状态与同种子输入；补候选数、接触次数、重复接触/零进展计数 | 新旧比较基准和阶段耗时，不复用非法初始阵列 |
| P1 原生状态访问 | 优先评估每Tick一次连续快照→Job内部连续读写→一次ECS回写，消除内层候选循环的重复组件查询 | 相同计算顺序下的位置、生命、生命周期、攻击/伤害/死亡序列与基线一致；所有权与清理通过 |
| P2 接触退化（按证据需要） | 若仍被重复零进展滑移拖慢，使用明确的二维有效约束收敛规则；保留扫掠最早接触和稳定等距顺序 | 斜向滑动、双侧夹角、紧密群体、初始接触、高速扫掠、地图边缘均不穿透、不抖动；解释数值精度处理 |
| P3 重新验收 | 普通Edit/Play回归、确定性专项、六组合法场地容量、正式关卡真实输入与退出清理 | 真实Burst、60Hz吞吐、完整60秒样本、欠账、GC、DrawCall和最终画面 |

优先采用能保持原计算顺序的访问优化；接触算法变更必须由计数与边界反例驱动。若CPU达标而整帧仍超预算，M1.5保持未通过，单独形成渲染批次方案。

### 已采用的实现收敛

P0计数确认大量接触没有位置进展。P1采用会话独占连续状态缓冲，Tick首尾各一次ECS读写。P2最终保留原边界夹取、ULP退让和单法线投影，仅在位置位模式完全不变的区间，用倍增检查点检测剩余位移的精确循环；重复状态后旧求解器的终点不会再变，可提前结束而无需减少原槽数上界或引入容差。该实现比新增投影规则更窄，原生新旧600 Tick完整状态指纹逐位一致。

## 验收标准

1. 正式表、生成物、手调Scene/Prefab无非预期变化；取消/重开/退出不留World、缓冲和句柄。
2. 现有普通回归全部通过；旧生命周期回调、技能预算、区域脉冲、精英/箱/胜负链无回归。
3. 新增接触边界与同种子同输入比较通过，记录允许的纯浮点误差，不能悄悄改变移动/伤害行为。
4. 三档共用固定测试场地/相机，目标存活数始终保持，所有单位在视野内，初始重叠/越界为0；基础与六超武各测一次。
5. 以现有表内目标验收：平均FPS≥60、帧P95≤16.67ms、测试热路径单帧GC≤1024字节、欠账不持续增长。Editor结果与将来的Player指标分开；不把短时阶段诊断当成容量通过。
