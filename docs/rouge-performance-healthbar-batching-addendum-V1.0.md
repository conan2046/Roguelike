# R2血条透明提交与合批补充方案 V1.0

2026-10-25。状态：用户已明确批准，继续内存原型、像素对照和验收。本补充只针对已批准表现方案中要求另行确认的透明排序提交变化，既有R0/R1/R3/R4不受影响。

## 证据与目标

本批共享快照、变化时写入已降低表现桥成本。实际Entities Graphics命令数与渲染实例数相同；当前包对HasSortingPosition实例采用每命令一个实例。基础负载中每怪主体加两层血条贡献约三条命令。材质原已开启实例化；当前没有单事件Frame Debugger证据或GPU时间，不把本问题归为单一Shader瓶颈。

## 推荐范围

先仅处理血条，单位主体、技能、数字继续现有Entities Graphics路径。保留正式血条图集、材质接口、Alpha混合、尺寸、锚点和前后层深度；不改Shader、URP、数值、表或Scene/Prefab。新方案改变血条透明提交和排序的承担方，因此按原V1.0的R2条款申请单独确认。

1. 先在隔离测试World制作仅驻留内存的血条批次原型，按当前相机的深度/层次构造有序几何。不得直接批量删除DepthSorted_Tag后宣称外观保持。
2. 使用同一权威状态、同一相机、同一目标，分别渲染原路径与原型；覆盖满血/缺血/死亡复用、重叠血条、密集怪群、场景边缘及不同相机位置。逐像素比较颜色和Alpha，并保留差异统计及两侧画面。排序平局或重叠不能等价时拒绝该原型，不放宽外观标准。
3. 仅在对照证明原有像素结果保持后，将血条提交迁入运行时批次。所有网格/缓冲从实际槽数增长，动态更新、重开、相机变更与退出均有明确所有权和释放；不保存任何预览资产。
4. 重新运行普通Edit/Play、真实入口回归和原六组完整容量协议。必须同时降低实际绘制命令数、保持人数/可见性/60Hz/GC预算并通过整帧目标，才计为性能修复。

## 风险与拒绝条件

| 事项 | 处理 |
|---|---|
| 同深度血条重叠、透明边缘顺序变化 | 对照不一致则拒绝；不以肉眼近似替代保持原外观 |
| CPU几何重建/顶点上传抵消收益 | 记录桥接/World/整帧及上传量；无收益则回退原路径 |
| 暂停、外部属性修改、同帧出生/死亡复用 | 消费现有共享权威快照，保留变化时更新，不新增默认配置 |
| 多相机或清场 | 明确每相机排序与运行时资源所有权；不向其他Unity项目发起操作 |
| 发现必须改Shader接口或URP路径 | 不包含在本补充中，另行给出证据和具体取舍 |

本补充不授权接受视觉差异、不保证该原型一定成功；批准后按上述拒绝条件持续推进，失败仍留证并保持M1.5未通过。

## 执行结果

已执行直接实例提交与不重叠条混合提交的内存原型，后者在六场景中仍有一场30个RGBA像素变化。依本补充的拒绝条件，两者均未落地；正式血条提交保持。结果见`rouge-performance-healthbar-prototype-report-20261025.md`。是否允许固定同深度重叠顺序的新取舍已另列文件并单独提问，不将本补充的批准扩展解释为允许视觉差异。
